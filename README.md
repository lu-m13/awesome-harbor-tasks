# Awesome Harbor Tasks [![Awesome](https://awesome.re/badge.svg)](https://awesome.re)

A curated list of [Harbor](https://github.com/harbor-framework/harbor) tasks, datasets, adapters and
related resources on GitHub.

Harbor is a framework for evaluating and optimizing agents and models in containerized environments,
and for generating RL rollouts. A **Harbor task** is a self-contained directory that defines what an agent
must do, the container it runs in, and how the result is verified.

## What is a Harbor task?

```
my-task/
├── task.toml          # config & metadata (name, version = "1.0", timeouts, env, gpus ...)
├── instruction.md     # what the agent is asked to do
├── environment/
│   └── Dockerfile     # the sandbox the agent works in
├── solution/
│   └── solve.sh       # oracle solution (should score 1.0)
└── tests/
    └── test.sh        # verifier; writes the reward
```

Quick start:

```bash
uv tool install harbor            # or: pip install harbor
harbor datasets list              # browse available datasets
harbor run -d "<dataset@version>" -a claude-code -m "<model>"
harbor trial start -p path/to/my-task -a <agent> -m <model>   # run a single task
```

## Adapters (existing benchmarks ported to Harbor)

Adapters live under `adapters/` in the Harbor repo and convert external benchmarks into Harbor task
directories. Examples include:

| Benchmark | Domain |
|---|---|

## Tools & Guides

- [Adapters guide (human)](https://www.harborframework.com/docs/datasets/adapters-human) — port an existing benchmark to Harbor.
- [Adapters guide (agent)](https://harborframework.com/docs/datasets/adapters) — full schemas, directory structure and validation criteria.
- `harbor adapters init <name>` — scaffold a new adapter; `harbor adapters validate adapters/<name>` — validate it.
- `harbor trial start -p <task>` / `harbor run -p <dataset>` — run one task or a whole dataset.

## Writing good tasks

- **Oracle first:** `solution/solve.sh` must pass `tests/test.sh` reliably (run it several times to catch flakiness).
- **Solvable, realistic, well-specified:** the instruction should contain everything the verifier checks.
- **Pin everything:** base image digest, package versions, upstream commits.
- **Enforce rules physically:** read-only files, offline mode, and permission boundaries rather than only prose rules.
- **Verify at build time:** fail the Docker build if the environment is wrong.
- **GPU tasks:** add a `docker-compose.yaml` with NVIDIA device reservations for Docker runs; set `gpus` in `task.toml` for cloud runs.
